# Audit Report — obsbot-mcp specs vs source (`<obsbot-mcp package root>`)

**Verification method:** every codec/transport/device/tools/capture file in `dist/` was read in full; the full 444-row opcode table was diffed programmatically against the spec's tables; the CRC check value and both worked frame examples were reproduced by executing the actual codec.

## Spot-checks requested (all pass)

- **CRC algorithm** — accurate. `crc.js:1-10` matches spec 1 §2 exactly (poly 0xA001 reflected, init/xorout 0xFFFF); executed `crc16usb("123456789")` = `0xb4c8` as claimed.
- **Frame header bytes** — accurate. `frame.js:3-25` matches spec 1 §1 (magic 0xAA, flags 0x25/0x01, len=const 12, CRC coverage/zeroed-token rules); both worked examples reproduced byte-for-byte by running `encodePtzMoveAngle(30,-10,0).buildFrame(1)` and `encodeVendorGet("AI_GET_GIM_BOOT_POS").buildFrame(2)`.
- **Status-block field offsets** — accurate. `commands.js:226-291` matches spec 1 §4 exactly (0x02 sleep, 0x04 zoomPct, 0x06 hdr, 0x07 faceAe, 0x11 fov, 0x18/0x1C aiMode m/n, 0x24 trackSpeed, min-length `<= 0x24` throw, all tables, m=6 transient rule).
- **Pan/tilt scale/sign conversions** — accurate. `linux.js:20` (3600 asec/deg), `linux.js:124-126` (`round(yaw*3600)`, `round(-pitch*3600)`), `linux.js:104-107` (get: float divide, no round), `linux.js:78-80` (range: rounded), `linux.js:150-158` (single-ioctl `pantilt_set` + `/unknown op/i` fallback to two parallel `camCtrlSet(…, 2)`), `linux.js:170-178` (speed-yaw negation).
- **Snapshot flow** — accurate. `helper-process.js:27-66,264-316` (isCompleteJpeg, maybeScaleJpeg args/qscale map/32 MiB/10 s, 4-attempt truncation retry, 30 000+settleMs timeout, busy→CameraBusyError, exact exhaustion message) and `tools.js:1598-1667` (auto-wake + 1500 ms, virtual/ndi name lookup, `maxDim` wire field, exact busy/no-source texts).

## Corrections (errors)

- **SPEC 1 §3c, `encodeSetExposure` — "`raw` range 0..65535" is a stale figure.** It was transcribed from an outdated comment block (`commands.js:88`); the device's actual exposure range is **1..2500**, read from `CAM_GET_EXPOSURE_RANGE_TINY2` (`tools.js:1552-1557`, and spec 3 §1.30 states it correctly). A port that maps percent→raw using 0..65535 from spec 1 will set wildly wrong exposures. Spec 1 should say: field is u32le; device-valid range 1..2500.
- **SPEC 1 §3a collision note is incomplete.** Three additional same-receiver wireCmd collisions exist (verified programmatically): `CAM_SET_FACE_FOCUS` / `CAM_SET_AFC_TYPE` both `0x3602` (`opcodes.js:11,107`), `CAM_GET_FACE_FOCUS` / `CAM_GET_AFC_TYPE` both `0x35C2` (`opcodes.js:12,106`), and `UG_GET_RESULT` / `UG_GET_UG_RESULT` both `0x0088` (`opcodes.js:417,423`). Any reverse map (wireCmd→name) or reply-matching logic built from the note's list alone is wrong for these.
- **SPEC 4 §1.2 — "result cached for process lifetime" is false on Linux.** `probeV4l2Devices()` never assigns `this.devices` (`dist/capture/manager.js:59-62,72-90`), so the `/dev` + sysfs probe re-runs on every `startRecord`/`startPreview`; only the dshow and avfoundation probes memoize (`manager.js:112,122`).
- **SPEC 3 §5 — "No env vars documented. Configuration is CLI-only (`--debug`)" is wrong as a behavioral statement.** Three environment variables change runtime behavior: `OBSBOT_LOG_FILE` (`dist/mcp/server.js:21`), `OBSBOT_OWNER_IDLE_TTL_MS` (`dist/ipc/coordinator.js:25` — idle-owner TTL, default 600 000 ms, 0 disables), `OBSBOT_RENDEZVOUS_NAME` (`dist/ipc/rendezvous.js:19` — IPC endpoint name). The claim is faithful to the README but a port implementing "CLI-only" loses all three knobs.
- **SPEC 3 §0.9 / spec 4 clarification — the "preset list unstable" error is retried, not terminal.** The double-read-empty check sits *inside* `readPresetSlots`'s try block (`tools.js:520-530`), so its throw is caught and consumes a retry attempt like any other read failure; it only propagates after all attempts (3) exhaust. Spec 3's wording ("→ throw") reads as an immediate hard failure.

## Additions (omissions that would break or degrade a port)

- **MAJOR: the entire IPC single-owner coordination subsystem is undocumented** (spec 3 §5 mentions it only as a "stale-owner trap" README aside). It is load-bearing — without it, two concurrently running server instances fight over the exclusive USB handle. Required behavior, all verified in source:
  - **Election** (`dist/ipc/rendezvous.js:19-68`): well-known endpoint `\\.\pipe\<name>` (win32) or `/tmp/<name>.sock` (POSIX), name default `"obsbot-mcp"`. `elect()`: try `listen` → owner; `EADDRINUSE` → `connect` → client; `ECONNREFUSED`/`ENOENT` on POSIX = stale socket → `unlink` + retry listen; 3 attempts total.
  - **Wire framing** (`dist/ipc/protocol.js:13-55`): `[uint32 BE body length][UTF-8 JSON]`, `MAX_FRAME` = 16 MiB (snapshots are the large case), `id`-correlated multiplexing; oversize frame = fatal, drop connection.
  - **Owner** (`dist/ipc/owner.js:5-43`): promise-chain queue runs one forwarded request at a time across all clients; errors become `{ok:false,error}` replies, never break the chain.
  - **Single-camera lock** (`dist/ipc/coordinator.js:10-17`, `dist/mcp/server.js:39-44`): `serialize()` wraps the tool dispatch so the owner's *local* MCP calls and forwarded client calls share one strict FIFO.
  - **Client + failover** (`dist/ipc/client.js`, `coordinator.js:105-120`): a client whose owner dies mid-call re-elects and retries **exactly once**.
  - **Idle-owner retirement** (`coordinator.js:24-97`): owner retires after 10 min idle (checked every TTL/4 clamped [5 s, 60 s], unref'd timer), closes its endpoint, and runs `onRetire` → `mgr.shutdown()` (`server.js:49`) so the next owner gets a clean camera claim; logs `obsbot-mcp: idle owner retired …` on stderr.
  - **Role logging**: `obsbot-mcp: ipc role=<owner|client>` printed to stderr at startup (`server.js:54`).
- **`dist/mcp/server.js` wiring is only partially covered across specs 3/4.** Missing: `process.on("exit"/"SIGINT"/"SIGTERM")` handlers call `capture.stopAll()`, `coordinator.close()`, `mgr.shutdown()` (`server.js:57-76`); ListTools advertises `zodToJsonSchema(tool.schema, {target:"jsonSchema7"})` (`server.js:87`); CallTool for an unknown name throws `unknown tool: <name>` (`server.js:92-94`); every call routes through `coordinator.dispatch`, with `renderToolResult` applied at the MCP boundary of the receiving instance (`server.js:98-99`).
- **SPEC 3 §1.32 / spec 2 tension worth stating in one place: snapshot's `resolution` silently depends on a local `ffmpeg`.** The helper always returns 1920×1080; downscaling is client-side `maybeScaleJpeg`, and if ffmpeg is missing/fails the full-size frame is returned with no error (`helper-process.js:40-66`). Spec 3's "snapshot … does not need ffmpeg" is true only in the sense that no image is *lost*; the `resolution` parameter becomes a no-op.
- **SPEC 1 §5.1 — `encodePresetSetName` has no length guard at the codec layer.** A payload > 44 bytes silently truncates at the 60-byte frame (`Buffer.copy` clamps, `frame.js:20`) while `len2` still records the full length and the payload CRC covers only the clamped segment — an internally inconsistent frame that `parseFrame` itself would reject as `truncated payload`. The 40-byte cap lives only in the tool layer (`tools.js:218,1431`); a port exposing the codec function directly should enforce ≤ 44 payload bytes (≤ 40 name bytes) there too.
- **Minor:** `HelperProcess` accepts a `commandOverride` argv (constructor, `helper-process.js:105,129`) and a fire-and-forget `send()` (`helper-process.js:377-379`) — test hooks a port's fake-helper tests will want. `index.js:26` additionally requires `process.argv[1] !== undefined` in the main-module guard.
- **Audit caveat:** the installed package ships only `native/prebuilt/<platform>-<arch>/` binaries — `native/linux/helper.c` is not present — so helper-internal claims (XU unit discovery, `v4l2_set_pantilt()`, `snapshot` op internals, Windows `g_knownPaths`) could not be source-verified here; everything about them in the specs matches the JS-side comments verbatim.
